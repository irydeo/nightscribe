# ADR-033: Versionado automático con setuptools-scm

**Estado / Status**: Accepted · **Fecha / Date**: 2026-09-10

## Español

**Contexto**: la versión del paquete (`"0.1.0"`) estaba hardcodeada en dos sitios
(`pyproject.toml` y `__init__.py`) que había que mantener a mano en sincronía.
No existían git tags, no había herramienta de versionado, y el hash git se
obtenía por separado en `version.py`. Cada release requería buscar y reemplazar
el número de versión en ambos ficheros.

**Decisión**: adoptar **setuptools-scm** para derivar la versión de git tags
automáticamente. No existe ningún número de versión hardcodeado en el código
fuente.

1. **`pyproject.toml`**: `version` pasa a ser `dynamic = ["version"]`. El
   construimiento requiere `setuptools-scm>=8`. Se configura con
   `version_scheme = "guess-next-dev"` y `fallback_version = "0.0.0"` (para
   árboles sin git: frozen builds, sdist).
2. **`nightscribe/__init__.py`**: `__version__` se obtiene de
   `importlib.metadata.version("nightscribe")` con fallback a `"0.0.0"`.
3. **`nightscribe/version.py`**: se añade `git_dirty()` que detecta working tree
   sucio. `full_version()` ahora muestra la cadena completa de setuptools-scm
   (p. ej. `0.2.0.dev3+g5c295cb`)加上 el hash corto y un `*` si hay cambios sin
   commitear.
4. **`nightscribe/__main__.py`**: se añade flag `--version` al parser principal;
   se elimina el import obsoleto de `__version__`.
5. **`.gitignore`**: se añade `nightscribe/_version.py` (generado por
   setuptools-scm en editable installs).

**Flujo de trabajo de releases**:

```bash
git tag v0.1.0        # marcar el commit del release
git push --tags       # publicar
pip install -e .      # reinstalar para actualizar la versión
```

Entre tags, cada commit incrementa automáticamente el número de dev. El esquema
`guess-next-dev` tras un tag `v0.1.0` produce `0.2.0.dev1+g<hash>` en el
siguiente commit.

**Tabla de comportamiento**:

| Situación | Versión |
|---|---|
| Commit con tag `v0.1.0` | `0.1.0` |
| 3 commits después del tag | `0.2.0.dev3+g5c295cb` |
| Working tree dirty | `0.2.0.dev3+g5c295cb.d20260910` |
| Sin git (frozen/sdist) | `0.0.0` (fallback) |

**Alternativas**: commitizen (requiere paso manual `cz bump` en cada release,
más control pero más fricción); hook pre-commit custom (no estándar, puede
causar conflictos en merges, difícil de mantener).

**Consecuencias**: la primera release requiere crear el tag base
(`git tag v0.0.0`); cada release requiere un `git tag` explícito; los builds sin
git (PyInstaller frozen) usan el fallback `0.0.0`; `__version__` en
`__init__.py` ya no se actualiza manualmente; `__main__.py` gana un flag
`--version` que faltaba.

## English

**Context**: the package version (`"0.1.0"`) was hardcoded in two places
(`pyproject.toml` and `__init__.py`) that had to be kept in sync by hand. There
were no git tags, no versioning tool, and the git hash was obtained separately
in `version.py`. Each release required searching and replacing the version number
in both files.

**Decision**: adopt **setuptools-scm** to derive the version from git tags
automatically. No version number is hardcoded in the source code.

1. **`pyproject.toml`**: `version` becomes `dynamic = ["version"]`. The build
   requires `setuptools-scm>=8`. Configured with `version_scheme = "guess-next-dev"`
   and `fallback_version = "0.0.0"` (for trees without git: frozen builds, sdist).
2. **`nightscribe/__init__.py`**: `__version__` is obtained from
   `importlib.metadata.version("nightscribe")` with a fallback to `"0.0.0"`.
3. **`nightscribe/version.py`**: `git_dirty()` is added to detect dirty working
   trees. `full_version()` now shows the full setuptools-scm string (e.g.
   `0.2.0.dev3+g5c295cb`) plus the short hash and a `*` when there are
   uncommitted changes.
4. **`nightscribe/__main__.py`**: a `--version` flag is added to the main parser;
   the obsolete `__version__` import is removed.
5. **`.gitignore`**: `nightscribe/_version.py` is added (generated by
   setuptools-scm in editable installs).

**Release workflow**:

```bash
git tag v0.1.0        # tag the release commit
git push --tags       # publish
pip install -e .      # reinstall to update the version
```

Between tags, each commit automatically increments the dev number. The
`guess-next-dev` scheme after a `v0.1.0` tag produces `0.2.0.dev1+g<hash>` on
the next commit.

**Behaviour table**:

| Situation | Version |
|---|---|
| Commit with tag `v0.1.0` | `0.1.0` |
| 3 commits after the tag | `0.2.0.dev3+g5c295cb` |
| Dirty working tree | `0.2.0.dev3+g5c295cb.d20260910` |
| No git (frozen/sdist) | `0.0.0` (fallback) |

**Alternatives**: commitizen (requires manual `cz bump` step per release, more
control but more friction); custom pre-commit hook (non-standard, merge-conflict
prone, hard to maintain).

**Consequences**: the first release requires creating the base tag
(`git tag v0.0.0`); each release requires an explicit `git tag`; builds without
git (PyInstaller frozen) use the `0.0.0` fallback; `__version__` in
`__init__.py` is no longer updated by hand; `__main__.py` gains the missing
`--version` flag.
